# 第二轮：壳，不是浏览器——同意目标，不同意这套实现

> 日期：2026-09-07  
> 状态：讨论稿。这一轮是对第一轮的修正，也是对「手机壳 / 把浏览器拉进壳」的反驳与合成。  
> 上一轮：[product-brief-v1.md](./product-brief-v1.md)

你们这轮把目标说清楚了，这比第一轮重要：

1. 不一定要做浏览器本体。可以做主动式服务框架，像手机壳套在浏览器外面。
2. 壳负责：主动辅助执行、记录偏好、点击、好奇内容、停留，并做抽取。
3. 明确反对现在的主流形态——用户打开侧栏、输入目标、Agent 代执行。那是用户发起的事件，不是 Agent 自主事件。

**目标我同意。实现我有三处不跟着走。** 下面用产品先例和技术约束来辩，最后给出一个合成后的形态。

---

## 1. 先把同意的部分钉死

上一轮最容易被误读的一句是「不要再做一只会聊天、会代点网页的 Chromium」。你们读成：我们连浏览器基础形态都可以不要。这个读法是对的。

更准确的共同立场：

> 产品不是「一个更聪明的地址栏」，而是 **一个会自己决定何时开口的服务运行时**。  
> 浏览器只是它观察和偶尔伸手的那块屏幕。

这和 2026 年几乎所有 AI 浏览器都反着来。Comet、Tabbit、Claude for Chrome、ChatGPT 扩展、夸克侧栏，主路径都是：

`用户产生意图 → 打开 Agent 表面 → 输入目标 → 模型执行`

你们要的是：

`系统先形成意图假说 → 决定开不开口 → 准备或轻辅助 → 人确认后才升格`

这个差异成立。不要再和他们比「侧栏谁更好用」。

## 2. 三处我不跟着走

### 反驳 A. 「把浏览器拉进壳」在工程上几乎一定会变成你们想避开的浏览器

手机壳是好的 **产品隐喻**，是坏的 **窗口架构**。

「拉进壳」如果从字面做，只有四条路。三条走不通，一条你们已经在第一轮倾向过。

| 做法 | 实际是什么 | 先例 | 为什么不成立 |
|---|---|---|---|
| 把用户正在用的 Chrome 窗口 SetParent 进自己的框 | 劫持别人的 HWND | 2000 年代套壳浏览器 | Chrome 不保证子窗口语义；macOS 基本做不到；一次大版本就能废 |
| 用 CDP / `--remote-debugging-port` 接管现有 Chrome | 调试协议当产品协议 | Chrome DevTools MCP、各类 Agent 继电器 | **Chrome 136 起默认用户目录不再理 remote debugging**。Google 就是为了防止第三方附着真实 profile。你能附着的，往往是一个空的新档案，不是用户每天用的那个 |
| 在自己的 App 里嵌 WebView2 / CEF / Electron，看起来像「壳住了浏览器」 | 你自己就是浏览器，只是功能残缺 | Wavebox Classic、Station、早期 Brave | 用户马上会要扩展、密码、PDF、WebAuthn、屏幕共享。Wavebox 公开写过：Electron 把「浏览器该有的东西」拆掉了，他们最后只能 **整棵迁去 Chromium fork** |
| 不装进框里，只用官方扩展 + 本机守护进程观察 Chrome | 外壳是服务，不是窗框 | Grammarly、Claude 扩展、Screenpipe 的浏览器部分 | 这是 2026 年唯一被允许、能活过明年的路 |

Wavebox 是最硬的反例。他们的产品哲学本来就是「工作壳」：把 Gmail / Slack / Notion 收进一个框。先用 Electron 当壳，很快发现时间都花在把浏览器功能补回去。2019 年他们放弃壳，改做 Chromium。Station 同一条路。Sidekick 这种工作区壳浏览器后来直接停了，用户退回 Chrome + 扩展。

所以：

> 如果你真的把 Chrome **视觉上装进自己的窗口**，12 个月后你大概率在修 PDF 和扩展，而不是在做主动服务。  
> 这正好是你们说「不一定需要浏览器基础形态」时想躲开的那个坑。

手机壳之所以成立，是因为它 **不替换触摸屏，也不重新实现蜂窝网络**。它只增加握持、MagSafe、按键。对应到浏览器：

- 握持 = 你的侧舱 / HUD / 每日简报窗口
- MagSafe = 吸附在 Chrome 旁边，而不是把它吞进去
- 按键 = 少数几个主动入口（卡点气泡、今日好奇、已准备好的草稿）

**壳应该是服务框架，不是父窗口。**

### 反驳 B. 「主动执行」比「主动准备」危险一个数量级；用户没下指令，就没有同意事件

你们说现在的 AI 浏览器都是用户发起，所以不是目标。诊断对。

但把目标写成「Agent 自主事件 + 辅助执行」，会把两件不同的事焊在一起：

| | 自主感知 | 自主行动 |
|---|---|---|
| 含义 | 自己判断「现在可能需要我」 | 自己去点、填、发 |
| 用户有没有同意瞬间 | 没有，所以开口成本必须极低、可无视 | 没有，所以出错不可逆 |
| 市面状态 | 几乎没人做好 | 巨头在做，且事故最多 |

用户主动输入目标，至少留下一个 **同意事件**：「我要你做这件事」。  
Agent 自己决定去做，同意事件不存在。提示词注入、假店、误提交、Amazon 诉 Perplexity 这类事，在「我叫它做的」里已经够糟；在「它自己做的」里，法律责任和信任会更差。

2026 年 9–10 月号 *ACM Interactions* 把这件事说死了：多智能体系统必须让人看见 **谁在行动、意图是什么、授权边界在哪、怎么打断和恢复**。自主执行如果做不到这四条，就不该做。

研究侧也在降温。2026 年的 PRISM 论文把主动干预建成两个概率：`P(需要帮助)` 和 `P(用户会接受)`，再用误报/漏报成本开门。另一篇 *Intervention Paradox* 更狠：干预准，也不等于干预有用；在高成功率任务上，乱插手会让成绩掉最多 26 个百分点。

翻译成产品语言：

> 自主性应该花在 **决定开不开口、准备什么**，不该花在 **决定按不按提交**。  
> 「辅助执行」可以有，但执行必须仍是人的手，或人刚点过的那一下。

否则你们不是在做手机壳。你们是在做会自己打电话的手机壳。

### 反驳 C. 记录「点击事件」会把产品讲成监视；「好奇」才是你们自己发明的、更好的对象

点击是底层传感器。停留是底层传感器。偏好、好奇、每日主题才是产品对象。

如果对外或对内的数据模型停在「点击事件流」，会同时踩三颗雷：

1. **叙事雷。** 用户听得懂「它知道我最近在好奇什么」，听不懂、也不会喜欢「它记录我每次点击」。
2. **商店雷。** Chrome Web Store 对 `<all_urls>` + 浏览历史 + 未召唤就读页面，走最严审查。一个「全网记录点击」的扩展，审核话术极差。Grammarly 能过，是因为它的主动范围被写成「你正在写的那一段」。
3. **信号雷。** 点击极噪。误触、关广告、点cookie横幅、狂点返回，都不是好奇。Screenpipe 已经从「每秒截屏」改成事件驱动：应用切换、点击、停顿、滚动停止、剪贴板变化才拍一帧。连做记录引擎的人都不存连续原始流。

「好奇内容」是这轮里最好的词。请把它升级成一等公民，把点击降级成实现细节。

好奇 ≠ 点击。一次有效好奇，通常是几种弱信号叠在一起：

- 停留超过阅读阈值（不是打开就关）
- 复访同一 URL / 同一主题
- 划词、复制、保存
- 在两个以上来源之间来回
- 滚动到深处而不是只看首屏

抽取的产出不该是日志，而该是用户能编辑的对象：

- 今日好奇：3–7 条
- 反复出现的偏好：站点、主题、对比维度
- 卡住的好奇：看了很多，没有形成决定

这比「我们记了你今天 846 次点击」更像产品，也更好做本地摘要，不必把原始事件送上云。

## 3. 历史：主动式不是蓝海，是坟场里的一块空地

「用户没叫，系统自己来」这条路，比 AI 浏览器老得多。不看这些，会重复它们的死法。

| 产品 | 它主动什么 | 后来怎样 | 教训 |
|---|---|---|---|
| Clippy | 你一打 Dear 就以为在写信 | 被默认关掉，骂了 25 年 | 推断准度低 + 太可见 + 关不干净 = 仇恨 |
| Google Now | 卡片在你问之前出现：航班、路况、日程 | 2012 年被称作年度创新；2016 年 Google **自己废掉品牌**，并进对话式 Assistant | 地球上最会做预测的公司，最后仍退回「你先说话」。原因不是技术做不到，是 **说不清为什么这张卡出现，误报成本高于漏报** |
| Cortana / 早期 Bixby | 系统级主动建议 | 边缘化 | 没有一个窄任务，主动就是骚扰 |
| Facebook M | 人工+模型主动办事 | 关停 | 主动办事的成本比主动提醒高一个数量级 |
| Humane / Rabbit | 环境计算，你不用打开 App | 硬件失败 | 「不用打开」不能补偿不准和慢 |
| Microsoft Recall | 先把一切记下来，事后再搜 | 舆论和监管差点打死它 | 记录本身可以是功能，但不能是默认云、不能是说不清的黑盒 |
| Cluely | 会议里隐形、主动给答案 | 伦理争议，CEO 后来承认虚报 ARR，产品往会议纪要撤退 | 「看不见的主动」一旦被理解成欺骗，品类会被污染 |
| Grammarly | 你正在写，它划线 | 活下来，2026 年还在 | **窄任务、现场、可忽略、准度高** |
| Dia Morning Brief | 早上给你日历和收件箱摘要 | 还在，但本质是定时任务，不是现场自主 | 「主动」常常只是闹钟，不是意图引擎 |
| Screenpipe | 本地记屏幕，给 Agent 当记忆 | 还在，偏开发者 | 记忆层有人做；**何时开口** 仍然空着 |

两句不好听但有用的话：

1. **Google 放弃了 Now，不是因为预测没价值，是因为「主动卡片」作为主界面养不活。** 它活下来的部分，变成了通知、Discover、Assistant 里的一小截。你们如果把主界面做成「不断自己跳出来的 Agent」，走的是 Now 被废掉的那条，不是 Grammarly 活下来的那条。
2. **活下来的主动，都长得像修正液，不像同事。** 它出现在你已经在做的动作上（写作、填表、离开一组标签），不出现在桌面中央宣布「我想到了」。

所以我同意「不要用户先输入目标」。  
我不同意「因此 Agent 应该自己发起一堆事件」。  
更稳的句子是：**Agent 自己形成假说，但只在少数高置信、可忽略的表面出现。**

## 4. 合成后的最优形态

把你们的壳，和我的反驳折中成一个东西：

> **Browser Companion：一个吸附在真实浏览器上的主动服务运行时。**  
> 不是新浏览器，不是把 Chrome 吞进父窗口，也不是侧栏对话框。

```text
┌──────────────────────────────────────────────┐
│  Companion Shell（你们的产品）                 │
│  · 今日好奇 / 偏好 / 未完成任务                 │
│  · 已准备好的草稿、对比、工作台                  │
│  · 策略：现在开不开口、开到哪一级                │
│  · 本地抽取内核                                │
└────────▲───────────────────────┬─────────────┘
         │ 观察（官方扩展+native） │ 建议 / 预填 / 草稿
         │                       ▼
┌────────┴─────────────────────────────────────┐
│  用户自己的 Chrome / Edge                     │
│  密码、扩展、同步、默认浏览器身份 全部不动        │
│  页内只有可关掉的一条气泡，没有常驻大侧栏         │
└──────────────────────────────────────────────┘
```

这仍然是手机壳。只是壳套在 **手机外面当配件**，不是把手机拆开焊进一个新机身。

### 4.1 三个表面，主表面不是聊天

| 表面 | 何时出现 | 像谁 | 不该像谁 |
|---|---|---|---|
| 页内一条 | 卡点、犹豫、离开前 | Grammarly 的划线 | Clippy、常驻侧栏 |
| 独立壳窗口 | 用户早上看、晚上收、中午自己点开 | Google Now 的卡片墙，但一天只更新几次 | 又一个 ChatGPT |
| 已准备好的托盘 | Agent 在后台写完对比/草稿后亮一个点 | 邮件里的「草稿已生成」 | 自动已发送 |

用户发起的对话可以有，但是三等公民。有人想深挖某条好奇，再打开。不要把「输入目标让 Agent 跑」做成首页——那正是你们要反对的形态。

### 4.2 数据模型：传感器 → 对象

```text
点击 / 停留 / 滚动 / 复制 / 复访     ← 本机，可销毁，默认不上云
                │
                ▼ 抽取
偏好 · 好奇条目 · 卡住的主题 · 今日摘要   ← 用户可见、可改、可删
                │
                ▼ 策略
沉默 | 页内一条 | 写入壳窗口 | 准备草稿 | 请求执行
```

第一期建议采集的，仍然比「全部点击」窄：

- 开：域名 + 可见停留、复访、复制、滚动深度、同一主题来回
- 开：表单停顿、rage click（只存「卡住」，不存字段值）
- 关：原始鼠标坐标、键盘内容、支付/银行/密码页
- 抽：每日好奇 3–7 条，而不是事件回放

「每天的使用偏好」不要做成仪表盘（那是 RescueTime，没人爱打开）。做成 **会自己改口的小档案**：「你最近在比三家 CRM 的定价」「你早上先看 GitHub 再看邮件」。用户能删掉一条，删掉后这类主动消失。

### 4.3 主动权的五级，默认停在 3

| 级 | 谁发起 | 谁动手 | 例子 |
|---|---|---|---|
| 0 静默抽取 | 系统 | 无人 |  tonight 的好奇列表更新了 |
| 1 壳内可发现 | 系统 | 无人 | 壳窗口多了一张「卡住的定价对比」 |
| 2 页内一条 | 系统 | 无人 | 「要不要预填？关掉即不再问这类」 |
| 3 准备好 | 系统 | 系统只写隔离草稿 | 对比表在托盘里，没提交任何网站 |
| 4 辅助执行 | **人点那一下** | 系统在可见步骤里点网页 | 用户点「帮我填」，才开始填 |
| 5 自主执行 | 系统 | 系统 | 不建议做。没有同意事件 |

你们要的「Agent 自主事件」= 0–3。  
「主动辅助执行」= 4，必须还人一个按钮。  
不要把 5 写进第一年。

这不是保守，是承认：自主感知是空白，自主行动是红海加雷区。

## 5. 和近邻怎么错位

| 近邻 | 像你们的地方 | 不像的地方 |
|---|---|---|
| Grammarly | 壳在真实 App 上，现场、可忽略 | 只懂写作，不懂好奇和任务 |
| Screenpipe | 本地记、事件驱动 | 它卖记忆 API，不卖「何时开口」 |
| Google Now | 先形成卡片再让你看 | 它没有「准备好的工作」；品牌已死，可学信号，别学主界面 |
| Dia Morning Brief | 早上看一眼 | 数据来自日历邮箱，不来自行为；一天一次闹钟 |
| Claude / Comet 侧栏 | 也能读当前页 | 主路径是你先输入目标 |
| Wavebox / Shift | 看起来像壳 | 它们最终是另一只浏览器，而且完全不主动 |
| Cluely | 不请自来 | 隐形 + 会议作弊，品类被污染，别学「看不见」 |
| Recall | 先记再搜 | 截图过重；没有主动准备 |

你们的一句话，建议改成：

> 它不换你的浏览器。  
> 它也不等你下命令。  
> 它只在你已经表现出好奇或卡住时出现，并且默认只准备，不提交。

## 6. 技术上第一期实际能做的

这是「壳」落地时不该幻想的部分。

**能做、该做**

- MV3 扩展：`tabs` / `webNavigation` / `idle` / 有限 content script
- Native messaging：本机加密库、抽取、策略
- 独立 Companion 窗口（Tauri / 原生日历那种小 App，不要 Electron 套网页再套网页）
- 页内气泡、Badge、托盘「已准备好」
- 本机小模型或规则先做聚类，云端只在用户点开某条好奇时才看到摘要

**不能当产品协议来用**

- 附着用户默认 Chrome 的 CDP（Chrome 136+ 已堵）
- 把官方 Chrome 嵌进自己的 HWND
- 在 WebView 里「假装这就是用户的 Chrome」（没有他的扩展和密码）
- 全量点击流上传

**辅助执行怎么接**

- 用户点「帮我填 / 对比」之后，再让扩展或独立 Agent 标签组动手
- 这一步可以复用 Browser Use / Playwright，不算你们的壁垒
- 没点之前，执行模块甚至不用加载——减少被说成木马的表面

Chrome Web Store 过审话术必须写成：

> 我们在本机抽取「你正在研究什么」，用来在你卡住时给你一条可关掉的建议。  
> 原始点击不上云。你能看见并删除每一条好奇。

不要写成：我们记录点击事件和停留时间。审核和用户都会按监视器理解。

## 7. 我建议的第一期，用来打你们的假设，不是用来做完整壳

假设要被证伪的是这三句，不是「我们会不会做浏览器」：

1. 用户能接受未被召唤的观察（装得住，不卸）
2. 未被召唤的建议会被点开，而不是被恨
3. 「今日好奇 + 一条卡住的准备」比侧栏对话框更常被用到

所以第一期可以小到：

- 扩展 + 本机库 + 一个 Companion 小窗
- 每天最多主动开口 N 次（先写死 5）
- 只产两种东西：今日好奇、一个「卡住主题」的准备稿
- 执行按钮可以有，但可以假：点了只打开准备稿，不真的去点网页

如果 2 失败，问题不在壳的形态，在主动本身——那就不要加执行，更不要去吞 Chrome。  
如果 2 成立，再把第 4 级「点一下才动手」接上。  
只有当 Companion 窗口被当成每天必开的东西，才讨论要不要更深地「包住」浏览器。到那时你们已经有理由了，而不是第一天就为了隐喻去嵌窗口。

## 8. 这一轮我坚持、也愿意被你们推翻的结论

1. **不要把 Chrome 拉进父窗口。** 隐喻保留，架构改成吸附。Wavebox / Station / Chrome 136 都在反对字面实现。
2. **自主事件 = 感知和准备，不是提交。** 否则你们比侧栏 Agent 更危险，而不是更先进。
3. **产品对象是好奇和偏好，不是点击流。** 点击只活在本机抽取器里。
4. **主界面不是聊天，也不是不断跳出来的 Agent。** 是一个一天看几次的壳，加上极少的页内一条。
5. **第一期用扩展证明主动，不证明壳能装下浏览器。**

如果你们坚持「必须视觉上把浏览器装进壳」，我需要听到一个 Wavebox 没遇到过的理由。目前我听到的理由（主动辅助、记录、抽取）全部可以在 **不吞窗口** 的前提下做完，而且更稳。
